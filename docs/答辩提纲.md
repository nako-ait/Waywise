# 《路书编译师 TripCompiler》答辩提纲

> 配套代码仓库即本目录的上级。本文档包含：5 分钟 Demo 脚本、PPT 逐页结构、口播词、
> 预判问答、兜底方案。**所有数字都是在未配置任何 API Key 的离线模式下实测得到的**，
> 现场可以一键复现（`backend/scripts/verify_all.py`）。

---

## 一、一句话定位（开场 15 秒）

> 传统旅行 App 让你「搜一个地方、看一条路线」；
> **路书编译师**让你「选一家酒店、在地图上圈几个想去的地方」，
> 它按地理位置、营业时间和交通便利度，用运筹优化算法把多日路书**编译**出来，
> 还能听懂一句人话改计划。

关键词：**酒店固定起点** · **地图标定** · **OR-Tools 求解** · **AI 可解释**

| 4:40–5:00 | 点「讲讲为什么这样排」 | 「AI 讲解，但数字全部来自求解器，不让模型编」 |

## 三、PPT 逐页结构（14 页）

### P1 封面
路书编译师 TripCompiler ｜ 以酒店为固定起点的 AI 多日路书编译器 ｜ 上海

### P2 问题：规划一次旅行，难在哪
- 搜得到景点，串不成路线：**顺序**是最耗心力的部分
- 顺序受多重约束：营业时间、换乘、花费、体力
- 通用大模型能"说"路线，但**不会真的求解**，也保不住事实
- 一句话卖点：**把"排序"这件事交给运筹优化，把"表达"交给大模型**

### P3 产品形态（一页截图）
左侧：AI / 酒店 / 主题线路 / 目的地列表 / 参数 / 便利度
右侧：地图（标记 + 路线 + 等时圈）
底部：时间轴 + 交通方式 + 统计

### P4 系统架构
```
前端 React + Vite + TS + 高德 JS API + Zustand + localStorage
        ↓ HTTP
后端 FastAPI
  ├── planner      编排：矩阵 → 分天 → 求解 → 精修 → 时间轴
  ├── OR-Tools     TSP/VRP 求解（时间窗 + 多目标 + 惩罚项）
  ├── 高德 Web 服务  距离矩阵 / 路径规划 / 地理编码（SQLite 缓存）
  ├── LLM          Function Calling（DeepSeek / 通义 / 智谱）
  └── 规则解析      无 Key 降级，保证离线可演示
```
一句话：**求解归求解，表达归表达，坐标只来自高德（GCJ-02）**。

### P5 核心算法：目标函数
```
弧成本(i→j) = w1×交通时间(分钟)
            + w2×[换乘次数×单次惩罚 + 方式不适感]
            + w3×费用(元)×3          ← 1 元 ≈ 3 分钟心理成本
            + w4×步行(km)×13.3       ← 4.5 km/h
总成本 = Σ弧成本 + 漏点惩罚(600 分钟/点) + 迟到惩罚(20 当量/分钟)
```
要点：所有项统一折算成**分钟当量**，所以权重滑杆是有物理意义的、可解释的。

### P6 约束怎么落地（这一页是技术分）
| 约束 | 实现 |
| --- | --- |
| 营业时间 | `CumulVar(i) ∈ [max(开门,出发), 关门-停留]` 硬约束 |
| 出发/收工 | 时间维度容量 + 终点 `SetCumulVarSoftUpperBound` 迟到惩罚 |
| 必去/可选 | `AddDisjunction(penalty)`：必去 1e7（等价硬约束）/ 可选 600 当量 |
| 午餐 | **两遍求解**：先探午餐落点，再把 60 分钟并进那一站的服务时间 |
| 酒店闭环 | `RoutingIndexManager(size, 1, [0], [0])` |
| 时间不够 | 丢点而不是无解，并**如实告诉用户丢了谁、为什么** |

### P7 多日：为什么不是一次性 VRP
- 酒店是每天共同的起点与终点 → 问题天然可分解
- 第一步 KMeans 地理聚类（纯 Python，等距圆柱投影 + k-means++）
- 第二步 时间均衡（把最重那天的边缘点挪给最轻那天）
- 第三步 每天各自 TSP
- 实测：12 个点分 3 天 → 4/5/3 点，约 **380/425/408 分钟**

### P8 AI：两条路径，同一份契约
- 有 Key：Function Calling（三个工具：解析地点 / 重规划约束 / 文本解释）
- 无 Key：规则解析（37 个 POI 的名称+别名最长匹配 + 偏好关键词）
- **两条路径产出同构参数** → 下游只有一份代码，端到端测试也只有一套
- 坐标永远不由模型给：地点 → 预置 POI / 高德地理编码 → 解析不到就报「未识别」

### P9 工程化：让演示不崩
- 距离矩阵 + 分段路径全部落 **SQLite 缓存**（TTL 7 天）+ 预热接口
- 无高德 Web Key → 自动离线估算，界面标注「离线估算」，**不假装是真数据**
- OR-Tools 缺失 → 自动降级纯 Python 贪心 + 2-opt，并把降级原因写进响应
- LLM 失败 → 自动降级规则解析，徽标显示真实来源
- POI 数据本地化（37 条），零网络也能演示

### P10 验证结果（贴 `verify_all.py` 的输出）
```
✅ 模块 1  POI 数据与接口冒烟        (1.3s)
✅ 模块 2  单日路线规划（5 种方式）   (24.5s)
✅ 模块 3  多日分天 + 等时圈         (32.2s)
✅ 模块 4  AI 解析 / 重规划 / 解释    (14.4s)
合计 4 个套件，通过 4 个，总耗时 72.3s
```
外加：`tsc --noEmit` 0 error；`vite build` 64 modules / gzip 68 kB。

### P11 踩过的坑（体现工程深度，挑 3 个讲）
1. **OR-Tools 9.15 的 `IntVar.SetSoftUpperBound` 不存在** → 求解器静默降级成贪心，路线质量悄悄变差。教训：**降级必须报出来**。
2. **午餐只在时间轴上加 60 分钟** → 求解器算时间窗时是"乐观"的，出现「16:45 关门的豫园被排到 17:06」。改成两遍求解，并保留独立推演器做交叉校验。
3. **OR-Tools 默认要求访问模型里每一个节点** → 多日模式下第 1 天会绕去第 2 天的目的地。修法：在 `solve()` 里做矩阵/节点契约检查，自动取子矩阵 + 下标重映射。

### P12 局限与下一步
- 公交/地铁耗时目前是「驾车时长 × 系数 + 换乘惩罚」的近似（真实公交路径逐段精修）
- 预算上限、多人偏好合并、天气重排尚未做
- P2：小红书攻略导入 / 截图 OCR 识别店名

## 四、预判问答（评委最可能问的 12 个）

**Q1：为什么不用一次性的 VRP，而要"先聚类再每天 TSP"？**
> 因为酒店是每天共同的起点和终点。把它建模成 7 天一个车队当然可以，但规模大、演示会卡，
> 而且结果不可解释。分天之后每天都是一个闭环 TSP，秒级收敛，还能对用户讲清楚
> 「第 1 天在黄浦-静安，第 2 天在浦东」。**可解释性本身是产品需求。**

**Q2：权重滑杆真的有用吗？我改了一下顺序没变。**
> 分两种情况：跨天的**地理分组**主要由距离决定，权重改不动它（这是正确的数学结果）；
> 但**天内的顺序和目标值**会变。实测：「极度厌恶步行」把
> `外滩→五角场→陆家嘴→七宝` 改成了 `外滩→陆家嘴→五角场→七宝`，目标值 488→485。
> 另外权重对**交通方式选择**影响更大，这也是我们把方式也做成可切换的原因。

**Q3：没有高德 Key / 没有 LLM Key 能演示吗？**
> 能，而且我们的测试默认就是在**没有任何 Key** 的情况下跑的。
> 距离走离线估算（直线 × 绕行系数），界面明确标注「离线估算」；
> AI 走规则解析，徽标显示「⚙️ 规则解析」。**我们不会把估算值伪装成实时数据。**

**Q4：营业时间约束怎么实现的？**
> 每个点的到达时刻是 OR-Tools 的 CumulVar，取值范围被限制在
> `[max(开门时间, 出发时间), 关门时间 - 停留时长]`。
> 如果某个点的营业窗口装不下停留时间，它会在建模前就被剔除并**报出原因**，
> 而不是排出一个"闭馆后参观"的荒谬结果。

**Q5：为什么午餐要两遍求解？**
> 第一版我们只在时间轴上事后加了 60 分钟，结果求解器算时间窗时是"乐观"的 ——
> 出现了「16:45 关门的豫园被排到 17:06 离开」这种自相矛盾的结果。
> 改成第一遍探午餐落点、第二遍把午餐并进那一站的服务时间，求解口径和时间轴就完全一致了。
> 我们还留了一个独立的 `schedule()` 做交叉校验，一旦不自洽立刻报警。

**Q6：AI 会不会瞎编地点或坐标？**
> 三道防线：① Prompt 里明确「绝对不要输出经纬度」；
> ② 坐标一律由后端补齐（预置 POI 命中 → 高德地理编码）；
> ③ 补不齐就原样返回「未识别」列表，绝不猜。
> 所以「今天天气不错」这种输入会明确告诉你没解析出地点，而不是随便给你标三个点。

**Q7：高德 API 限流怎么办？**
> 三层：① 距离矩阵用「1 终点 × 多起点」批量接口，N 个点只要 N 次请求；
> ② 所有结果落 SQLite 缓存（TTL 7 天），并提供了 `/api/plan/prewarm` 预热接口，
> 演示前跑一次，现场全部命中本地缓存；③ 37 个 POI 本地化，搜索不打网络。

**Q8：这个和直接用大模型规划有什么区别？**
> 大模型给的是"看起来合理的路线"，我们要的是"**可证明较优且满足约束**的路线"。
> 在我们的架构里，**排序永远是求解器做的**，大模型只做两件它擅长的事：
> 把自然语言翻译成结构化参数、把求解结果讲成人话。它无权直接输出路线。

**Q9：地图上标记点击会不会误触发新增点？**
> 这是高德开发的经典坑。我们做了三重保险：自定义标记的 DOM 事件全部 `stopPropagation`、
> overlay 设 `bubble:false`、地图 click 再用 400ms 时间戳兜底。
> 因为不同版本的 JS API 冒泡行为不一致，只靠一层不保险。

**Q10：为什么 POI 数据只有 37 个？**
> 演示数据是"够用且可控"的取舍：37 个覆盖了上海主要片区与玩法标签，
> 足以体现聚类分天、营业时间窗、等时圈这些能力，而且**零网络依赖**。
> 生产环境下接高德 POI 搜索即可，代码里已经有 `PlaceSearch` 与地理编码的通路。

**Q11：坐标系怎么保证不乱？**
> 全链路只有一个坐标来源：高德 GCJ-02。前端地图点击、PlaceSearch、后端地理编码，
> 全部产出 GCJ-02，不做任何转换；`types/index.ts` 与 `models.py` 都写了这条约定。
> 冒烟测试里还有一条断言：所有 POI 必须落在上海的经纬度包围盒内。

**Q12：如果要接入更多城市呢？**
> 城市相关的东西目前只有三处：`SHANGHAI_POIS` 数据、地名解析用的别名表、
> 高德的 `citycode`（现在写死 `021`）。把这三处参数化就是多城市版本，
> 算法层（聚类/求解/时间轴）与城市无关。

## 五、兜底方案（演示前 5 分钟检查清单）

1. **预热缓存**：`python scripts/verify_all.py` —— 四套件全绿再上台（同时把缓存捂热）
2. **提前开好两个终端**：后端 `python run.py`、前端 `pnpm dev`，浏览器打开 127.0.0.1:5173
3. **看页头胶囊**：显示「● 后端就绪 · ortools」才开讲；红色就按提示重启后端
4. **录屏兜底**：完整 Demo 录一遍（含 AI 重规划与多日切换），任何一环崩了直接切录屏
5. **准备一张"离线也能演"的底牌**：不填任何 Key 就是全离线路径，
   把 `frontend/.env.local` 里的 Key 注释掉即可复现（评委问起直接演给他看）

**如果 AI 接口超时**：面板会显示降级警告，功能照常（`source=rules`）。
**如果地图加载失败**：页面会显示 Key 配置引导卡片，不是白屏。
**如果后端没启动**：页头胶囊变红，底栏会给出启动命令。
